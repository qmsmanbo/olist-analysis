# 对账日志 · 我是怎么确保数据可信的

> 目的：记录本项目里「两套实现结果不一致」的每一次，以及原因和修正。
> 用途：说明结论如何校验、问题如何定位。

## 一、方法：双路对账

同一个指标，用两条**独立的技术路径**各算一遍：

```
路径 A：MySQL 里写 SQL（交付物，别人能重跑）
路径 B：Python/pandas 直接读 CSV 算（我自己的第二实现）
```

对上了 → 口径一致、代码都没错。
对不上 → **必须解释清楚，不能含糊过去**。

**本次结果**：共触发 7 次不一致，全部定位到原因——4 次引擎语义、2 次我方错误、1 次口径分歧。
其中 2 次是我自己算错，已修正并补了校验。

为什么不做单路：只有一条路时，错了没有任何信号；两条路时，差异会自己暴露出来。

## 三、四类差异，四种处理

| 类型 | 特征 | 处理方式 |
|---|---|---|
| **口径分歧** | 两边代码都没错，但对「超时/复购」的定义不同 | 选一个写进文档，两边统一；报告里注明另一口径的结果 |
| **引擎语义** | SQL 与 pandas 的默认行为不同（截断、空值、排序） | 显式指定行为，写进代码注释 |
| **代码 bug** | 有一边写错了 | 改错的那边，并补一条校验 |
| **数据理解错** | 你对数据的假设错了（如「主键唯一」） | 最危险——回到数据体检，重新确认 |

## 四、四个高频陷阱

### 1. 时间差：整天 vs 精确

```python
# pandas：保留小数（12.56 天）
(delivered - purchase).total_seconds() / 86400
```
```sql
-- MySQL：只数日期差（12 天）
DATEDIFF(delivered, purchase)
```

**影响**：超时率 8.11% → 6.77%。「超时 6 小时」在 SQL 里算 0 天。

### 2. 分组：空值算不算一类

```python
df.groupby("category")["price"].sum()            # 默认丢 NaN 分组
df.groupby("category", dropna=False).sum()       # 保留
```
```sql
GROUP BY category                                -- NULL 自成一类
```

**影响**：占比分母差 1.33%。

### 3. 计数：数行 vs 数非空

```sql
COUNT(*)              -- 行数（LEFT JOIN 后包含空行）
COUNT(o.order_id)     -- 非空的行数（LEFT JOIN 后是 0）
```

**影响**：补零分析里，用错会让「没有订单的那天」显示成 1。

### 4. 口径不一致：对账两边不是同一批订单

对账金额时有两条路，但很容易忘了先确认订单范围：

```sql
-- A：按明细汇总
SELECT SUM(price + freight_value) FROM order_items;          -- 15,843,553.24

-- B：按支付汇总
SELECT SUM(payment_value) FROM order_payments;               -- 16,008,872.12
```

两者差 165,318.88（1.04%）。第一反应是「有退款」或「运费没算进去」，但都不是。

把口径统一到 `delivered` 之后：

| 口径 | 明细合计 | 支付合计 | 差额 |
|---|---|---|---|
| 全量订单 | 15,843,553.24 | 16,008,872.12 | 165,318.88（1.04%） |
| **仅已送达** | **15,419,773.75** | **15,422,461.77** | **2,688.02（0.02%）** |

**差额几乎全部来自非已送达订单**（取消、不可用、处理中）——这些订单可能已收款但未发货、或已退款。
把口径对齐后，剩下的 0.02% 属于金额舍入。

> 教训：**对账之前先确认两边是不是同一批订单。** 口径没对齐时，「差 1%」看起来像数据错误，实际上只是比了两群人。

## 五、可复用的检查清单（十项）

取数之后，按这十项自查：

| # | 检查 | 做法 |
|---|---|---|
| 1 | **量级** | 数量级对吗？DAU 跑出 100 就是错了 |
| 2 | **恒等式** | 总数 = 各维度加总？GMV = 客单价 × 订单数？ |
| 3 | **主键唯一** | `COUNT(*)` vs `COUNT(DISTINCT 主键)` |
| 4 | **空值率** | 关键字段的空值占比，是否超出预期 |
| 5 | **时间范围** | `MIN/MAX` 是否在预期窗口内 |
| 6 | **分布形状** | 中位数 vs 均值，有没有极端长尾 |
| 7 | **同比/环比** | 和上一期比，突变就是信号 |
| 8 | **双路对账** | 换一种工具/口径再算一遍 |
| 9 | **抽样明细** | 抽 10 条，手工验算一遍 |
| 10 | **业务方对数** | 问一句「这个数你看着合理吗」 |

## 六、异常值：检测 ≠ 删除

本项目**几乎没有剔除异常值**，这是刻意的：

| 现象 | 处理 | 理由 |
|---|---|---|
| 配送 210 天 | **保留** | 它就是最严重的履约失败，删掉就看不见问题了 |
| 1 星评价 | **保留** | 分析对象 |
| 客单价 2,372 元 | **保留** | 真实大单，删掉会低估客单价 |
| 负的配送时长 | 检查过：0 行 | 如果有，那是数据错误，必须剔除 |
| 配送时长 = 0 | 检查过：0 行 | 同上 |

**原则**：先判断是「数据错误」还是「真实极端值」。

- 真实极端值 → **保留**，必要时单独分析
- 数据错误（负时长、未来日期、测试单）→ 剔除，并**记录剔除了多少、为什么**

**删除异常值不是「让数据好看」，是「修正错误」。前者是造假。**
